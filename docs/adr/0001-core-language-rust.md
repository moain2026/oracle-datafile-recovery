# 0001 — لغة النواة: Rust + ربط بايثون
## السياق والمشكلة
النواة تحلّل بايتات غير موثوقة (ملفات تالفة/معادية) بأحجام تصل إلى تيرابايتات. نحتاج: أمان ذاكرة (لا انهيار ولا ثغرات من ملف مُعدّ)، أداء قريب من سرعة القرص، ثنائي واحد بلا اعتماديات لعملاء على Windows/Linux، وسهولة تجارب الاستدلال.
## الخيارات
1. **Rust** (+ PyO3 لبايثون) 2. Go 3. C/C++ (كـ DUL/ODU) 4. بايثون فقط (كـ oradul/RICO2) 5. Java (كـ DBRECOVER)
## القرار (اعتمده المالك 2026-10-15: "أعلى المعايير")
الخيار 1: Rust للنواة (`odr-core`, `odr-cli`)، بايثون عبر PyO3 لمحرّك الاستدلال والتجارب.
## العواقب
- ✔ أمان ذاكرة بلا GC؛ zero-copy على mmap؛ توازي آمن (rayon)؛ `cargo fuzz` جاهز؛ ثنائي ساكن واحد.
- ✔ بايثون يبقى للبحث (إحصاء، ML) دون أن يكون في المسار الحرج للأداء.
- ✘ منحنى تعلم أعلى وبطء تطوير أولي مقارنة ببايثون. تخفيف: النموذج الأولي لـ M1/M2 يمكن أن يُكتب بايثون كـ "مرجع مرجعي" (oracle) للتحقق ثم يُنقل.
- ✘ Go أبسط لكن GC وضعف SIMD/zero-copy؛ C++ أسرع تطويراً لفريق متمرّس لكن خطر الذاكرة على مدخلات معادية غير مقبول.
- ✔ Windows أولاً: هدف `x86_64-pc-windows-msvc` مع CRT ساكن (`.cargo/config.toml`) ← `odr.exe` واحد يعمل على أي Windows Server بلا تثبيت أي شيء؛ CI يبني ويختبر على Windows قبل Linux.
